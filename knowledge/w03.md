## Day 1 · Tokenization：模型眼中的文字

**一句话**：模型不读字符，它读 token；token 数直接决定成本、上下文和延迟。

**核心知识**

- BPE 从字符开始，反复合并高频相邻片段，形成子词词表；WordPiece/SentencePiece 思路类似但细节不同。
- 中文 token 效率取决于词表和训练语料；同一句话在不同模型上 token 数可能差很多。
- 特殊 token（BOS/EOS/pad/system）参与对话模板；模板不一致会影响效果。
- 上下文窗口按 token 计，不是按字数；长文档要切分或压缩。
- 成本按输入/输出 token 分别计费，输出通常更贵。

**速查**

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
ids = enc.encode("Java 后端转 AI 开发")
print(len(ids), ids)
```

**常见坑**

- 用“1 个汉字 = 1 个 token”估算成本，实际可能差 1.5–2 倍。
- 只算输入 token，忽略输出和重试；真实账单会高很多。

**面试口述**

> 为什么同一个中文句子在不同模型上 token 数不同？这会带来什么工程影响？

**深入理解**
- **机制**：BPE 从字符开始合并高频片段，词表大小和合并规则决定切分；特殊 token 参与对话模板。
- **边界**：token 数不等于字符数；同一句话在不同模型上不同；长上下文按 token 计费。
**场景**：中文知识库按真实文档统计 token，估算 embedding 和生成成本，不要用“1 字=1 token”。
**追问**：Q：怎么降低 token 成本？A：裁剪上下文、摘要、缓存、批量、选更高效词表的模型，并监控输出 token。

**任务关联**：token 统计脚本 / 中英代码对比 / 成本报告

## Day 2 · Embedding 与相似度

**一句话**：embedding 把语义压成向量，检索就是在向量空间里找“最近的意思”。

**核心知识**

- embedding 模型把文本映射到固定维度向量；语义相近的文本距离更近。
- 余弦相似度看夹角，点积看方向和模长；向量归一化后两者排序等价。
- 维度、语言、领域、最大输入长度都会影响模型选择；MTEB 可参考但不能代替业务评测。
- 相似不等于相关：同义句可能很近，反义句也可能很近（取决于模型）。
- 检索失败常见原因：切分切断语义、模型不适配领域、query 太短、距离度量不匹配。

**速查**

```python
import numpy as np
def cosine(a, b):
    a, b = np.asarray(a), np.asarray(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
```

**常见坑**

- 把 embedding 当“关键词匹配”，忽略 query 改写和混合检索。
- 不做归一化就直接比较点积，长文本会占便宜。

**面试口述**

> 余弦相似度和点积什么时候等价？为什么很多模型建议先归一化？

**深入理解**
- **机制**：embedding 把文本映射到同一向量空间，余弦看夹角；归一化后点积与余弦排序等价。
- **边界**：不同模型向量不可混用；短 query 与长文档语义密度不同；领域词可能不在模型分布内。
**场景**：用 bge-m3 建库，先归一化再算余弦；query 太短时配合关键词/改写。
**追问**：Q：什么时候需要微调 embedding？A：领域术语多、召回长期不达标、有标注数据时；先试更好的通用模型和混合检索。

**任务关联**：20 句向量 / top-k / 失败案例分析

## Day 3 · Attention 与 Transformer Block

**一句话**：self-attention 让每个 token 根据相关性聚合其他 token 的信息。

**核心知识**

- Q/K/V：Q 与 K 点积得到相关性权重，softmax 归一化后加权聚合 V。
- 缩放因子 `sqrt(d_k)` 控制点积方差，避免 softmax 饱和和梯度消失。
- 多头让模型在不同子空间关注不同关系（语法、指代、位置等），最后拼接。
- 位置编码提供顺序信息；残差 + LayerNorm 让深层网络稳定训练。
- FFN 做逐 token 非线性变换；encoder/decoder 结构决定注意力可见范围。
- 复杂度随序列长度平方增长，长上下文需要额外优化。

**速查**

```python
def attention(Q, K, V):
    scores = Q @ K.T / (Q.shape[-1] ** 0.5)
    weights = np.exp(scores - scores.max(axis=-1, keepdims=True))
    weights /= weights.sum(axis=-1, keepdims=True)
    return weights @ V
```

**常见坑**

- 只背“QKV”，讲不清“每个词如何看其他词”；面试官一追问就露馅。
- 把 attention 权重直接当“解释”，它只是相关性，不是因果。

**面试口述**

> self-attention 为什么要除以 sqrt(d_k)？多头的作用是什么？

**深入理解**
- **机制**：Q 与 K 点积得到相关性，softmax 归一化后加权 V；多头在不同子空间学习不同关系。
- **边界**：标准 attention 是 O(n²)；attention 权重不是因果解释；pre-norm/post-norm 影响训练稳定性。
**场景**：长文档不是无限塞上下文，而是切分/检索；需要位置编码和残差保证深层训练。
**追问**：Q：为什么除以 sqrt(d_k)？A：控制点积方差，避免 softmax 饱和和梯度消失。

**任务关联**：attention 实现 / 热力图 / 3 分钟白板稿

## Day 4 · 预训练、SFT 与 RLHF

**一句话**：预训练学语言，SFT 学指令，RLHF/DPO 学偏好。

**核心知识**

- 预训练：海量无标注文本，目标是下一个 token 预测；得到基座模型。
- SFT：指令-回答对，教模型跟随指令、输出格式；数据质量决定上限。
- RLHF：用人类偏好训练奖励模型，再用 RL 优化；DPO 直接用偏好对优化，工程更简单。
- 基座模型不等于助手模型；instruct 版本经过后训练，更会“听话”。
- 灾难性遗忘：窄领域微调可能损害通用能力，要混入通用数据并做回归。

**速查**

```text
预训练 → SFT → 偏好优化（RLHF/DPO）
数据：无标注文本 → 指令对 → 偏好对
目标：语言建模 → 指令跟随 → 有用/无害/风格
```

**常见坑**

- 以为什么都能靠微调解决；知识更新、权限、引用更适合 RAG。
- SFT 数据只追求数量，格式不统一、答案错误，模型会学坏。

**面试口述**

> SFT 和 RLHF 分别解决什么问题？为什么不直接上 RLHF？

**深入理解**
- **机制**：预训练学下一个 token，SFT 学指令-回答映射，RLHF/DPO 用偏好优化有用性和安全性。
- **边界**：SFT 数据质量决定上限；偏好数据昂贵；窄领域微调可能灾难性遗忘。
**场景**：企业助手先用 RAG 解决知识更新，再用 SFT 固定输出格式和领域语气。
**追问**：Q：DPO 和 PPO 的区别？A：DPO 直接用偏好对优化，工程简单；PPO 需要奖励模型和 RL 训练，控制更复杂。

**任务关联**：训练阶段图 / base vs instruct 对比 / 阶段笔记

## Day 5 · 解码、采样与成本

**一句话**：模型输出的是概率分布，采样策略决定“稳定”还是“多样”。

**核心知识**

- greedy 每步选最高概率；beam search 保留多个候选，适合翻译等任务。
- temperature 缩放 logits：越低越稳定，越高越发散。
- top-k 只保留概率最高的 k 个；top-p 保留累计概率达到 p 的最小集合。
- stop 控制停止词；max_tokens 控制成本上限；seed 不保证跨平台完全复现。
- temperature=0 也不保证确定性：浮点、批处理、硬件、模型版本都会带来差异。

**速查**

```text
抽取/问答：temperature 0–0.3，top_p 0.8–1.0
创意写作：temperature 0.7–1.0，top_p 0.9–1.0
代码生成：temperature 0–0.2，明确 stop 和 max_tokens
```

**常见坑**

- 同时大改 temperature 和 top_p，无法归因；一次只调一个。
- 把 temperature=0 当成“可复现实验”，线上仍可能漂移。

**面试口述**

> temperature 和 top-p 的区别？事实型任务怎么配？

**深入理解**
- **机制**：模型输出是概率分布，temperature 缩放 logits，top-p 截断累计概率，stop/max_tokens 控制终止和成本。
- **边界**：temperature=0 也不保证跨平台复现；temperature 和 top-p 同时大改无法归因；输出 token 通常更贵。
**场景**：抽取/问答用低温 + 明确 stop；创意任务提高温度，但用评测控制质量。
**追问**：Q：logprobs 有什么用？A：看模型置信度、做分类/打分、排查异常输出，但不等于事实正确。

**任务关联**：采样实验 / 参数表 / 推荐配置

## Day 6 · 模型选型与评测

**一句话**：选模型不是选“最强”，而是在质量、延迟、成本、合规之间找约束最优。

**核心知识**

- 先定质量门槛和 SLO，再比较模型；没有约束的选型没有意义。
- 小模型做基线，大模型看上限；用固定评测集比较，不看排行榜单。
- 评测维度：正确性、格式合法率、忠实度、延迟、成本、稳定性。
- 本地模型收益是隐私/成本/可控，代价是质量、运维和硬件。
- 供应商锁定、限流、版本变更、数据合规都要纳入决策。

**速查**

```text
选型表字段：模型 / 质量 / P95 / 单价 / 上下文 / 部署方式 / 风险
结论格式：在满足 X 的前提下，选 Y，因为 Z；如果约束变成 W，会换 V。
```

**常见坑**

- 只看几个“顺眼”的样例就选型；没有评测集，无法复现。
- 忽略模型版本更新导致的输出漂移。

**面试口述**

> 怎么为一个业务任务选模型？你会用哪些指标做决策？

**深入理解**
- **机制**：模型选型是约束优化：质量门槛、P95、成本、上下文、部署方式、合规。
- **边界**：排行榜不等于业务效果；模型版本更新会漂移；本地模型省 API 费但增加运维和硬件成本。
**场景**：先用小模型建立 baseline，再用大模型看上限；固定评测集比较。
**追问**：Q：怎么评估一个模型是否适合业务？A：固定任务集 + 人工抽检 + 延迟/成本/稳定性，和 baseline 对比。

**任务关联**：模型对比 / 评测表 / 选型结论

## Day 7 · 周复盘：LLM 原理

**一句话**：从 token 讲到生成，能把每一步的取舍讲清楚，就够面试用了。

**核心知识**

- 一条主线：tokenizer → embedding → Transformer → logits → 采样 → 自回归。
- 三个工程约束：上下文窗口、延迟、成本。
- 三种后训练：SFT、RLHF、DPO；知道各自目标即可。
- 幻觉的根因是“预测下一个 token”，RAG/引用/拒答是缓解，不是根治。

**速查**

```text
本周最小验收：
[ ] 能白板画 Transformer block
[ ] 能解释 temperature/top_p
[ ] 能算一次请求成本
[ ] 能说出 3 个模型选型维度
[ ] 能口述幻觉与 RAG 的关系
```

**常见坑**

- 把“参数量大”当成唯一优势，忽略延迟和成本。
- 背论文名词但讲不出工程含义。

**面试口述**

> 用 3 分钟从 token 讲到生成。

**深入理解**
- **机制**：整条链路是 tokenizer → embedding → Transformer → logits → 采样 → 自回归；每一环都有成本和误差。
- **边界**：RAG 缓解幻觉但不根除；上下文窗口有限；attention 不是数据库查询。
**场景**：用 3 分钟从 token 讲到生成，再举一个幻觉/引用失败的例子。
**追问**：Q：temperature=0 为什么还会不稳定？A：浮点、批处理、硬件、模型版本和外部检索结果都会变化。

**任务关联**：W3 周测 / 白板录像 / LLM 速查表 / 周报
