# W05 · Embedding 与 RAG 基础

> 阶段：LLM 与 RAG 核心（P1）｜Day 1–7
> 用法：先读当天小节，再去做学习舱任务；做完回来补“常见坑”。

## 本周主线

- 搭出最小 RAG 闭环：解析 → 切分 → embedding → 检索 → 生成 → 引用。
- 用评测集定位问题，而不是凭感觉调参。
- 把“检索失败”拆成五类原因，形成排查顺序。

## Day 1 · Embedding 模型与向量库选型

**一句话**：先选“够用且可运维”的组合，再谈性能极限。

**核心知识**

- 选 embedding：语言/领域、维度、最大输入长度、成本、是否可本地部署。
- pgvector 适合已有 Postgres 的团队：事务、权限、metadata filter 都能复用。
- 专用向量库（Qdrant/Milvus）在超大规模、复杂过滤、分布式上更强，但多一套运维。
- HNSW 参数：`m` 连接数、`ef_construction` 建索引候选、`ef_search` 查询候选；越大召回越高、资源越多。
- 距离函数要与模型训练时一致（cosine/inner product/L2）。

**速查**

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  doc_id text NOT NULL,
  tenant_id text NOT NULL,
  content text NOT NULL,
  embedding vector(1024)
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
```

**常见坑**

- 只看 benchmark 选模型，不看中文/领域/长文本表现。
- 距离函数和索引 opclass 不匹配，召回结果会很奇怪。

**面试口述**

> pgvector 的 HNSW 参数 m、ef_construction、ef_search 分别影响什么？

**深入理解**
- **机制**：HNSW 用多层图做近似最近邻，上层稀疏负责快速跳转，下层稠密负责精细搜索；m 决定连接度，ef 决定候选集。
- **边界**：ef_search 越大召回越高但延迟越大；m 越大内存越多；过滤条件太多时 HNSW 可能退化为扫描。
**场景**：已有 Postgres 的团队先用 pgvector，事务、权限、metadata filter 复用；超大规模再评估专用向量库。
**追问**：Q：HNSW 和 IVF 怎么选？A：HNSW 查询快、召回好但内存高；IVF 更省内存、适合大批量，需调 nlist/nprobe。

**任务关联**：pgvector 最小检索 / 选型 ADR / 20 条向量

## Day 2 · 文档解析与切分

**一句话**：切分是 RAG 最容易被低估、但收益最大的环节。

**核心知识**

- 解析要保留结构：标题、段落、表格、页码、来源；这些是 metadata 和引用的基础。
- 切分策略：固定窗口、递归分隔符、按标题/段落、语义切分、parent-child。
- chunk 太小丢上下文，太大稀释 embedding、增加噪声和成本；常见 300–800 token，重叠 10–20%。
- 中文按标点/段落切；代码按函数/类切；表格单独处理。
- metadata：tenant、doc_id、version、title、page、section、chunk_index。

**速查**

```python
def recursive_split(text, size=600, overlap=80):
    # 先按段落，再按句子，最后按字符；保证不超过 size
    ...
```

**常见坑**

- 直接按固定字符切，把一句话/表格切断，召回后模型也读不懂。
- 不存原文位置，引用无法定位到页码/段落。

**面试口述**

> 为什么按标题/段落切分通常比固定窗口好？什么时候反而适合固定窗口？

**深入理解**
- **机制**：解析保留结构，切分把长文档变成可检索单元；chunk 是检索和生成的共同上下文单位。
- **边界**：固定窗口会切断句子/表格；chunk 太大稀释 embedding；metadata 缺失会导致无法过滤和引用。
**场景**：技术文档按标题层级切，再按 token 上限二次切；表格单独转文本并保留表头。
**追问**：Q：chunk size 怎么定？A：先按结构切，再用评测集做 300/500/800 token 消融，同时看召回、忠实度和成本。

**任务关联**：3 个文档解析 / 递归切分 / 长度分布 / metadata

## Day 3 · 向量检索、过滤与 MMR

**一句话**：top-k 不是越大越好；先保证“能召回”，再保证“不重复、不越权”。

**核心知识**

- 相似度检索返回 top-k；k 增大召回可能上升，但噪声、延迟、成本也上升。
- metadata filter 必须下推到检索层，不能先全库召回再在应用层过滤。
- MMR 在相关性和多样性之间权衡，减少重复 chunk；lambda 越接近 1 越重相关性。
- 多租户/权限过滤要进入查询条件，缓存 key 也要带租户。
- 召回失败先看：query、切分、embedding、filter、索引参数。

**速查**

```python
def mmr(query_vec, candidates, k=5, lam=0.7):
    selected = []
    while len(selected) < k:
        best = max(candidates, key=lambda c: lam * c.score - (1 - lam) * max_sim(c, selected))
        selected.append(best)
    return selected
```

**常见坑**

- 为了“召回更多”把 k 调到 100，结果上下文塞满噪声，答案更差。
- 只在应用层过滤租户，导致越权和召回数量不足。

**面试口述**

> MMR 解决什么问题？lambda 怎么权衡？

**深入理解**
- **机制**：向量检索返回 top-k，filter 缩小候选空间，MMR 在相关性和多样性间做贪心选择。
- **边界**：先全库召回再过滤会越权且召回不足；k 太大会引入噪声；MMR 会增加计算。
**场景**：多租户检索把 tenant_id 下推到 SQL；同一文档重复 chunk 用 MMR 去重。
**追问**：Q：MMR 的 lambda 怎么调？A：问答偏相关（0.7–0.9），探索型任务可降低；用评测看答案质量和重复率。

**任务关联**：retrieve 函数 / filter / MMR / 10 个 query 相关性

## Day 4 · 上下文拼装、引用与拒答

**一句话**：引用不是装饰，是让答案可验证、让错误可定位的基础设施。

**核心知识**

- 上下文拼装：按相关性排序、控制 token 预算、保留来源/页码、避免重复。
- 引用粒度越细越好：chunk id + 原文片段 + 页码/段落。
- 生成后校验引用 id 存在、片段确实在上下文中、答案能被片段支持。
- 无证据时拒答；拒答阈值要在评测集上调，权衡误拒和漏拒。
- 拒答也要给下一步建议（缩小范围、补充文档、转人工）。

**速查**

```text
Prompt 约束：
只依据 <context> 回答；每个结论后标注 [1][2]；
context 中没有答案时，输出“根据现有资料无法确定”，并说明缺什么。
```

**常见坑**

- 让模型“自由发挥”，再补引用；引用和答案对不上。
- 拒答太激进，用户问什么都说不知道；要用评测调阈值。

**面试口述**

> 怎么让引用可信，而不是装饰？

**深入理解**
- **机制**：context assembly 把候选 chunk 排序、去重、裁剪到 token 预算；citation 把答案片段映射回来源。
- **边界**：引用 id 必须存在且真的支持结论；无证据应拒答；上下文顺序会影响模型注意力。
**场景**：每个 chunk 带 id/页码/标题，prompt 要求输出 [n]；生成后校验引用存在和片段匹配。
**追问**：Q：怎么判断引用是否支持答案？A：规则校验 id + 原文包含，再用 NLI/LLM 判断蕴含，最后人工抽检。

**任务关联**：answer 函数 / 引用校验 / 拒答测试 / 10 条问答

## Day 5 · 最小 RAG 评测

**一句话**：没有评测集，你无法知道是检索坏了还是生成坏了。

**核心知识**

- 评测集：question、reference answer、relevant chunk ids、是否可回答。
- 检索指标：Recall@K、MRR、命中率；生成指标： faithfulness、答案相关性、引用命中。
- 失败分类：切分、召回、排序、上下文、生成、引用、权限。
- 人工抽检不可省；自动指标有偏差。
- 评测集要版本化，改动后跑回归。

**速查**

```text
Recall@5 = 前 5 个结果中命中相关 chunk 的 query 数 / 总 query 数
```

**常见坑**

- 只用模型生成的题，题目和文档分布不一致。
- 只看一个总分，不定位失败类型，无法改。

**面试口述**

> Recall@K 和 faithfulness 分别衡量什么？一个高另一个低说明什么？

**深入理解**
- **机制**：评测集把“我觉得好”变成可比较的数字；检索指标和生成指标要分开看。
- **边界**：Recall@K 高不代表答案好；faithfulness 高也可能是“只回答安全的部分”；评测集会被调参污染。
**场景**：20 条问题覆盖单跳、多跳、无答案、表格和权限边界；记录相关 chunk id 和参考答案。
**追问**：Q：怎么避免自己出题自己满分？A：题源来自真实用户/文档 FAQ/专家，保留 held-out，人工抽检并做跨版本对比。

**任务关联**：20 条评测 / baseline / 失败聚类 / 报告 v1

## Day 6 · Lab：mini-rag 原型

**一句话**：先跑通闭环，再逐步替换每个环节。

**核心知识**

- 最小架构：ingest → chunk → embed → store → retrieve → prompt → answer → cite。
- 先做 CLI/单文件，再做 API；先 SQLite/pgvector，再考虑专用向量库。
- 增量索引用内容 hash + 唯一约束/upsert，失败任务可重试。
- 评测脚本独立于 UI，能命令行复现。
- README 写清架构、启动、评测结果、已知问题。

**速查**

```text
mini-rag/
├─ ingest.py
├─ retrieve.py
├─ answer.py
├─ eval.py
└─ data/
```

**常见坑**

- 一开始就上复杂框架，出问题不知道是哪一层。
- 不保存 chunk 原文和 metadata，引用/排查都做不了。

**面试口述**

> 你的 RAG baseline 架构是什么？三个瓶颈在哪？

**深入理解**
- **机制**：最小 RAG 是 ingest → chunk → embed → store → retrieve → prompt → answer → cite 的闭环。
- **边界**：先跑通再优化；没有 chunk 原文和 metadata，引用/排障都做不了；没有评测无法比较。
**场景**：先用 CLI 和 pgvector 跑 20 条评测，再包 FastAPI；每次改动只动一个环节。
**追问**：Q：第一个瓶颈通常在哪？A：切分和召回最常见；先用失败样本定位，不要一上来换模型。

**任务关联**：mini-rag / 增量索引 / 20 条评测 / 架构图

## Day 7 · 周复盘：RAG 基础

**一句话**：RAG 的每个环节都要有指标，否则优化就是碰运气。

**核心知识**

- 能画出完整链路并标注失败点。
- 能解释 chunk size/overlap 的取舍。
- 能说清 metadata filter 为什么必须在检索层。
- 能用 Recall@K 和 faithfulness 区分检索/生成问题。

**速查**

```text
本周最小验收：
[ ] 3 种格式文档可入库
[ ] top-5 检索可复现
[ ] 引用能定位到原文
[ ] 20 条评测有 baseline
[ ] 能口述 5 类失败原因
```

**常见坑**

- 只关注“答得漂亮”，忽略“引用是否正确”。
- 评测集只在最后做，前期改动没有基线。

**面试口述**

> 用 3 分钟讲 RAG 全链路和失败模式。

**深入理解**
- **机制**：RAG 的失败可以分层：解析/切分、embedding、召回、排序、上下文、生成、引用、权限。
- **边界**：不同层的症状可能相似（答错），必须用 trace 和评测区分；没有 baseline 无法归因。
**场景**：用户说“答案不对”，先看相关 chunk 是否召回，再看排序、上下文、引用和生成。
**追问**：Q：Recall@K 高但答案差，可能是什么？A：上下文噪声、排序靠后、模型没用证据、prompt 约束不足或引用错位。

**任务关联**：W5 周测 / 链路图 / GitHub 仓库 / 周报
