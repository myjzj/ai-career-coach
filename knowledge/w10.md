# W10 · LangGraph 与工作流

> 阶段：Agent 工程（P3）｜Day 1–7
> 用法：先读当天小节，再去做学习舱任务；做完回来补“常见坑”。

## 本周主线

- 用状态图表达控制流，而不是把所有逻辑塞进 prompt。
- 掌握 checkpoint、中断恢复、人工审批和多智能体。
- 让工作流可测试、可观测、可恢复。

## Day 1 · StateGraph：把 Agent 画成状态机

**一句话**：能用代码表达的控制流，不要交给模型即兴发挥。

**核心知识**

- StateGraph：节点（函数）处理状态，边决定下一步；条件边按状态分支。
- 状态 schema 要明确字段和 reducer；多个节点更新同一字段时的合并规则很关键。
- 节点职责单一：解析、检索、生成、校验、执行，各自可测试。
- 普通边是固定顺序；条件边用于分支、重试、循环、审批。
- 先把图画出，再写代码；图就是架构。

**速查**

```text
入口 → 解析 → 检索 → 生成 → 校验
                         ├─ 通过 → 输出
                         └─ 失败 → 重试/拒答
```

**常见坑**

- 节点做太多事，失败无法定位。
- 状态字段没有 reducer，消息/候选被覆盖。

**面试口述**

> LangGraph 的条件边解决什么问题？相比 while 循环的优势？

**深入理解**
- **机制**：StateGraph 用节点处理状态、边控制流转；条件边根据状态选择分支。
- **边界**：状态字段没有 reducer 会被覆盖；节点职责过多难定位；图太复杂难维护。
**场景**：解析→检索→生成→校验，校验失败走重试/拒答分支。
**追问**：Q：什么时候用子图？A：可复用的多步子流程，或需要独立状态/权限的模块。

**任务关联**：4 节点图 / 状态契约 / 状态图 / 5 个输入

## Day 2 · Checkpoint 与中断恢复

**一句话**：checkpoint 让工作流可以暂停、恢复、重放，而不是只能从头再来。

**核心知识**

- checkpointer 持久化每步状态；thread_id 隔离不同会话。
- 支持失败恢复：从最后一个成功节点继续。
- 支持人工审批：暂停后隔天恢复，不阻塞进程。
- 支持时间旅行：回到某步，修改状态重跑。
- 生产用 Postgres/Redis 持久化，注意并发、清理和隐私。

**速查**

```text
thread_id = tenant + conversation_id + workflow_id
checkpoint = 状态快照 + 下一步 + 时间戳
```

**常见坑**

- thread_id 冲突，两个用户共享状态。
- checkpoint 存了敏感信息，没有加密/过期策略。

**面试口述**

> checkpoint 解决什么问题？thread_id 为什么关键？

**深入理解**
- **机制**：checkpoint 持久化每步状态，thread_id 隔离会话；支持恢复、审批和时间旅行。
- **边界**：thread_id 冲突会串状态；持久化敏感信息要加密/过期；并发写要处理冲突。
**场景**：节点失败后从最后一个成功 checkpoint 恢复，不从头重跑。
**追问**：Q：checkpoint 存什么？A：状态、下一步、时间戳、版本；不要存无法序列化的对象。

**任务关联**：checkpointer / 失败恢复 / 3 个恢复测试

## Day 3 · Human-in-the-loop：审批、修改、恢复

**一句话**：审批不是弹窗，是状态机里一个可恢复的节点。

**核心知识**

- 在关键动作前 `interrupt`，持久化待审批动作、参数、风险说明、发起人、过期时间。
- 审批结果：通过 / 拒绝 / 修改参数；都要写入状态。
- 恢复前重新校验参数、权限和时效；审批期间环境可能变化。
- 拒绝要走终止分支，不能只有“通过”。
- 审批记录进审计日志，支持追责。

**速查**

```text
状态：pending_action = {tool, args, risk, requested_by, expires_at}
恢复：validate(args, permission, expires_at) → execute / reject
```

**常见坑**

- 审批只存在内存，服务重启后丢失。
- 恢复时直接执行，不校验参数是否被篡改。

**面试口述**

> 人工审批节点怎么设计状态？恢复前为什么要重新校验？

**深入理解**
- **机制**：interrupt 在关键动作前暂停，状态持久化；resume 时重新校验并继续。
- **边界**：审批只存内存会丢；恢复前不校验参数/权限会执行被篡改的动作；拒绝分支必须存在。
**场景**：发送通知/执行 SQL 前审批，支持改参、拒绝、超时。
**追问**：Q：审批状态包含什么？A：待执行工具、参数、风险、发起人、过期时间、决策和修改记录。

**任务关联**：审批节点 / 修改/拒绝/超时 / 1 分钟演示

## Day 4 · 多智能体：supervisor 与专家

**一句话**：多智能体不是高级版，是另一种权衡。

**核心知识**

- supervisor 负责分派任务、汇总结果；专家 Agent 负责具体领域。
- handoff 传递任务和上下文；共享状态要定义清楚。
- 多 Agent 增加通信成本、状态不一致、调试难度和延迟。
- 适合：任务可清晰分工、需要并行探索、不同工具权限。
- 不适合：简单强顺序任务；先用单 Agent + 好工具。

**速查**

```text
supervisor → research_agent
           → sql_agent
           → writer_agent
           → 汇总/校验
```

**常见坑**

- 为多而多，最后成功率不如单 Agent。
- 共享状态没有版本/锁，专家之间互相覆盖。

**面试口述**

> 多智能体什么时候是反模式？怎么判断是否值得拆？

**深入理解**
- **机制**：supervisor 分派任务给专家 agent，汇总结果；共享状态和通信协议决定可靠性。
- **边界**：多 agent 增加通信成本、状态不一致、延迟和调试难度；简单任务不需要。
**场景**：研究 agent + SQL agent + writer agent，由 supervisor 编排。
**追问**：Q：什么时候多 agent 是反模式？A：任务强顺序、共享状态复杂、收益低于通信成本时。

**任务关联**：supervisor / 2 个专家 / 单 vs 多对比

## Day 5 · 流式、可观测与任务评测

**一句话**：非确定性系统要看分布，不看单次成败。

**核心知识**

- 流式事件：节点开始/结束、工具调用、token、错误；前端可展示进度。
- 节点级 trace：输入、输出、耗时、token、错误。
- 任务评测：固定任务集 + 成功标准，多次运行看成功率、步数、成本、干预率。
- 失败分类：规划错、工具错、参数错、观察误读、循环、权限。
- 允许波动，报告分布和置信区间，不报单点。

**速查**

```text
20 条任务 × 3 次 = 60 次运行
指标：成功率 / 平均步数 / P95 成本 / 人工干预率
```

**常见坑**

- 只跑一次成功就宣布可用。
- 只看成功率，不看步数和成本。

**面试口述**

> 怎么评测一个非确定性的 Agent？

**深入理解**
- **机制**：节点级 trace 记录输入/输出/耗时/token/错误；任务评测看成功率、步数、成本和干预率。
- **边界**：单次成功不代表稳定；只看成功率不看成本会得出错误结论。
**场景**：20 条任务 × 3 次运行，报告分布和失败分类。
**追问**：Q：非确定性系统怎么评测？A：固定任务集、多次运行、人工抽检、统计分布和置信区间。

**任务关联**：节点 trace / 10 条任务 / 指标表

## Day 6 · Lab：带审批的运营工作流

**一句话**：把状态图、checkpoint、审批、trace 串成一个能演示的闭环。

**核心知识**

- 流程：查数据 → 生成报告 → 审批 → 发送/执行 → 汇总。
- 审批支持通过/拒绝/改参/超时；拒绝走终止分支。
- 高风险动作前暂停；恢复前重新校验。
- trace 记录每步；失败可从 checkpoint 恢复。
- demo 要展示“暂停→改参→恢复”，这是差异化。

**速查**

```text
Demo 脚本：
1. 发起任务
2. 在审批节点暂停
3. 修改参数/拒绝
4. 恢复执行
5. 展示 trace 与结果
```

**常见坑**

- 演示只走“通过”，没有拒绝/修改，看不出可控性。
- 审批和执行业务逻辑耦合，无法单独测试。

**面试口述**

> 用 2 分钟讲你的工作流状态机。

**深入理解**
- **机制**：运营工作流是“查数据→生成报告→审批→执行→汇总”的状态机。
- **边界**：审批/执行耦合难测试；没有拒绝/超时分支不算可控；没有 trace 无法排障。
**场景**：演示暂停、改参、恢复、拒绝四条路径。
**追问**：Q：工作流怎么测试？A：节点单测 + 图级集成测试 + 失败恢复测试 + 审批分支测试。

**任务关联**：审批工作流 / 10 条任务 / README / demo

## Day 7 · 周复盘：LangGraph

**一句话**：显式状态 + 可恢复执行，是复杂 Agent 的生产化基础。

**核心知识**

- 能画状态图并解释每个节点/边。
- 能说清 checkpoint、thread_id、interrupt/resume。
- 能设计审批状态和拒绝分支。
- 能判断多智能体是否值得。

**速查**

```text
本周最小验收：
[ ] 状态图可运行
[ ] 失败可恢复
[ ] 审批可暂停/恢复
[ ] 有节点级 trace
[ ] 能讲单 vs 多 Agent 取舍
```

**常见坑**

- 只学 API，不理解状态和恢复，线上排障困难。
- 把审批当 UI 弹窗，服务重启就丢。

**面试口述**

> LangGraph 相比 while 循环的优势？代价是什么？

**深入理解**
- **机制**：显式状态 + 可恢复执行是复杂 agent 的生产化基础；while 循环适合简单任务。
- **边界**：框架增加学习成本；状态设计不好会比 while 更难维护。
**场景**：面试时对比 while 循环和 LangGraph 的恢复、审批、观测能力。
**追问**：Q：LangGraph 的代价是什么？A：抽象和依赖增加，简单任务过度设计。

**任务关联**：W10 周测 / 项目二状态图 / 周报
