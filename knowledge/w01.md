## Day 1 · 从 Java 到 Python：语法、容器与推导式

**一句话**：Python 的容器、切片和推导式是内置表达式，先用它们消灭 Java 式 for 循环。

**核心知识**

- `list` 是动态数组：下标 O(1)，中间插入/删除 O(n)；`dict` 是哈希表：平均 O(1)，key 必须可哈希。
- `tuple` 不可变，适合做字典 key 或返回多值；`set` 用于去重和集合运算。
- 切片 `[start:stop:step]` 左闭右开，负索引从末尾算；切片会创建新对象（浅拷贝）。
- 推导式 `[f(x) for x in xs if cond]` 比手写 append 更清晰；dict/set 也有推导式。
- `is` 比较对象身份，`==` 比较值；小整数/字符串驻留会让 `is` 偶尔“看起来对”，但不要依赖。

**速查**

```python
nums = [1, 2, 3, 4]
squares = [x * x for x in nums if x % 2 == 0]
word_count = {}
for w in ["a", "b", "a"]:
    word_count[w] = word_count.get(w, 0) + 1

first, *rest = nums          # 解包
matrix_t = list(zip(*[[1, 2], [3, 4]]))  # 转置
unique = list(dict.fromkeys([3, 1, 3, 2]))  # 去重保序
```

**常见坑**

- 可变默认参数 `def f(x, acc=[])` 会在多次调用间共享同一个 list；用 `None` 再创建。
- `for i in range(len(xs))` 通常是 Java 思维；优先 `for x in xs`、`enumerate`、`zip`。

**面试口述**

> Python 的 list 和 dict 底层分别是什么？为什么 dict 查找平均 O(1)？

**深入理解**
- **机制**：list 是连续数组，扩容时重新分配并均摊 O(1)；dict 是哈希表，冲突时探测，扩容会 rehash，所以最坏 O(n)。
- **边界**：dict 只保证插入顺序，不保证有序遍历；自定义对象做 key 必须实现 __hash__/__eq__，参与哈希的字段要不可变。
**场景**：日志去重保序用 dict.fromkeys；元素是 dict/list 时先转成可哈希的 tuple 或 JSON 字符串，注意嵌套结构。
**追问**：Q：list.sort() 和 sorted() 有什么区别？A：前者原地排序返回 None，后者返回新列表；都稳定，支持 key/reverse。

**任务关联**：语法练习 / textkit 包 / ADR-001 / 3-2-1 复盘

## Day 2 · 函数、类、类型与异常

**一句话**：Python 用“协议 + 组合”替代大量继承，用 dataclass 和 typing 把数据结构写清楚。

**核心知识**

- 函数参数：位置参数、关键字参数、`*args`、`**kwargs`；默认参数在定义时求值一次。
- 闭包保存外层作用域变量；`nonlocal` 才能修改外层局部变量。
- `@dataclass` 自动生成 `__init__/__repr__/__eq__`；可变字段用 `field(default_factory=list)`。
- `Protocol` 是结构化子类型：只要方法签名匹配就满足，不需要显式继承。
- 异常要分层：业务异常、配置异常、外部依赖异常；用 `raise ... from e` 保留因果链。
- 上下文管理器 `with` 保证资源释放；可实现 `__enter__/__exit__` 或用 `contextlib.contextmanager`。

**速查**

```python
from dataclasses import dataclass, field
from typing import Protocol

@dataclass
class Document:
    id: str
    text: str
    tags: list[str] = field(default_factory=list)

class Tokenizer(Protocol):
    def encode(self, text: str) -> list[int]: ...

class ConfigError(Exception):
    pass
```

**常见坑**

- 类型注解不会在运行时强制校验；需要校验就用 Pydantic 或显式检查。
- 捕获 `Exception` 后不要静默 `pass`；至少记录上下文并决定是否重试。

**面试口述**

> Python 的 Protocol 和 Java interface 有什么区别？

**深入理解**
- **机制**：Protocol 是结构化子类型，runtime_checkable 只检查属性是否存在，不校验签名；dataclass 生成 eq/repr，frozen=True 才不可变。
- **边界**：异常不要静默吞掉；上下文管理器要覆盖异常路径；可变默认值必须用 field(default_factory=...)。
**场景**：用 Tokenizer Protocol 替换 API 与本地实现，service 只依赖协议，不依赖具体类。
**追问**：Q：ABC 和 Protocol 怎么选？A：需要显式继承、共享实现用 ABC；解耦第三方实现、做 duck typing 用 Protocol。

**任务关联**：textkit 包 / Tokenizer 实现 / ADR / 复盘

## Day 3 · 工程化：uv、pytest、ruff 与配置

**一句话**：让 Python 项目像 Java 项目一样可克隆、可测试、可重复构建。

**核心知识**

- `pyproject.toml` 是项目元数据与依赖的中心；`uv.lock` 锁定精确版本，保证可复现。
- `uv sync` 创建虚拟环境并安装依赖；`uv run pytest` 在项目环境中执行命令。
- pytest fixture 提供测试依赖；作用域 `function/class/module/package/session` 决定复用范围。
- `parametrize` 用数据驱动多个用例；`tmp_path` 提供隔离的临时目录。
- ruff 同时做格式化和 lint；pre-commit 在提交前自动检查。
- 日志用标准库 `logging`，不要用 print 代替生产日志；配置结构化输出便于检索。

**速查**

```bash
uv init
uv add httpx pydantic
uv add --dev pytest ruff
uv run pytest -q
uv run ruff check .
```

**常见坑**

- 测试之间共享全局状态/数据库会互相污染；用 fixture 建独立环境并在 teardown 清理。
- 只测“正常路径”不够；异常、超时、空输入、边界值才是 bug 高发区。

**面试口述**

> pytest fixture 的作用域有哪些？怎么避免测试互相污染？

**深入理解**
- **机制**：pyproject 声明依赖，uv.lock 固定解析结果；pytest fixture 用依赖注入管理测试资源，session 作用域只创建一次。
- **边界**：session fixture 里的可变状态会跨用例污染；数据库测试可用事务回滚或 truncate，不要依赖执行顺序。
**场景**：CI 用 uv sync --frozen 安装锁定版本，保证本地与流水线一致。
**追问**：Q：autouse fixture 有什么风险？A：隐式依赖、难追踪、可能拖慢测试；只在全局必要（如日志捕获）时使用。

**任务关联**：pyproject / 10 个测试 / ruff 配置 / README

## Day 4 · 异步、HTTP 与第一个流式 LLM 调用

**一句话**：LLM 调用是典型的“高延迟 I/O”，异步和流式是体验与成本的关键。

**核心知识**

- `async def` 定义协程，`await` 让出事件循环；不要在异步函数里调用阻塞 SDK。
- `asyncio.gather` 并发执行多个协程；要配超时、取消和异常处理。
- `httpx.AsyncClient` 持有连接池，应复用；每个请求新建 client 会丢失连接复用。
- SSE 是单向 server→client 的文本协议：`data: ...` 行 + 空行分隔事件。
- 上游错误要分类：401 不重试、429 退避、5xx 有限重试、超时取消。
- token 统计从响应 `usage` 取；流式响应可能只在最后一块返回 usage。

**速查**

```python
async with httpx.AsyncClient(timeout=30) as client:
    async with client.stream("POST", url, json=payload, headers=headers) as r:
        async for line in r.aiter_lines():
            if line.startswith("data: "):
                chunk = line[6:]
                if chunk == "[DONE]":
                    break
                print(chunk)
```

**常见坑**

- API key 不要写进代码或提交到 Git；用环境变量/密钥管理。
- 流式解析要处理半行、空行、`[DONE]` 和异常中断，不能假设每个 chunk 都是完整 JSON。

**面试口述**

> SSE 和 WebSocket 的区别？为什么 LLM 流式常用 SSE？

**深入理解**
- **机制**：协程在 await 处让出事件循环，适合高并发 I/O；SSE 用 data 行和空行分隔事件，客户端逐事件消费。
- **边界**：在 async 函数里调用阻塞 SDK 会卡住整个循环；流式 usage 可能只在最后一块返回；代理缓冲会让流式失效。
**场景**：上游 429 时读取 Retry-After，做指数退避 + 抖动；客户端断开要取消上游请求。
**追问**：Q：asyncio.gather 中一个任务抛异常会怎样？A：默认向外传播，其他任务可能继续；需要 TaskGroup 或 return_exceptions 控制。

**任务关联**：llm_client / 真实 API 基线 / 错误处理 / 成本记录

## Day 5 · CLI 整合：配置、重试与成本

**一句话**：把零散脚本组装成有配置、有日志、有预算的可演示工具。

**核心知识**

- 配置优先级：环境变量 > 配置文件 > 默认值；敏感信息只从环境变量读。
- CLI 参数用 argparse/typer；子命令和 `--help` 是可维护性的一部分。
- 重试只对可重试错误；指数退避 + 抖动，尊重 `Retry-After`。
- 会话历史要存全量，但发给模型时只取最近 N 轮 + 摘要。
- 成本 = 输入 token × 输入单价 + 输出 token × 输出单价；流式也要统计。
- 日志记录 request id、模型、耗时、token、错误类型，便于排障。

**速查**

```python
import random, time

def backoff(attempt: int) -> float:
    return min(30, 2 ** attempt) * (0.5 + random.random())
```

**常见坑**

- 无限重试会把小故障放大成雪崩；必须设最大次数和总预算。
- 只统计“成功请求”的成本会低估真实花费；失败/重试也要计。

**面试口述**

> 怎么设计一个可测试、可观测的 LLM 客户端？

**深入理解**
- **机制**：配置优先级让部署环境覆盖默认值；重试通过退避把瞬时故障摊开，抖动避免大量客户端同时重试。
- **边界**：非幂等操作不能盲重试；失败/重试请求也可能计费；用字符数估算 token 会严重低估成本。
**场景**：给 CLI 设日预算，超过阈值停止调用并提示；日志记录 request id、模型、token、延迟和错误类型。
**追问**：Q：重试和熔断的区别？A：重试处理瞬时故障；熔断在持续失败时快速失败，保护下游和调用方。

**任务关联**：llm-cli / 多轮与摘要 / 成本上限 / 8 个测试

## Day 6 · Lab：把 CLI 变成可演示作品

**一句话**：可运行、可解释、可复现，比功能多更重要。

**核心知识**

- 项目结构：入口层（CLI）→ 配置层 → 客户端适配层 → 会话/存储层。
- 适配器模式隔离不同模型供应商；业务逻辑不直接依赖某家 SDK。
- 上下文溢出策略：滑动窗口、摘要、检索相关历史、分层记忆。
- 测试用 mock transport 构造普通响应、流式 chunk、超时和错误。
- 演示脚本：问题 → 方案 → 现场操作 → 结果 → 限制，控制在 3 分钟。

**速查**

```text
llm-cli/
├─ pyproject.toml
├─ src/llm_cli/
│  ├─ cli.py
│  ├─ config.py
│  ├─ client.py
│  └─ session.py
└─ tests/
```

**常见坑**

- 摘要会丢细节；用户偏好、硬约束、未完成事项要结构化保留。
- 演示时不要从安装依赖开始讲；先让观众看到问题和结果。

**面试口述**

> 对话历史超过上下文窗口时，你怎么处理？

**深入理解**
- **机制**：Adapter 隔离供应商差异；上下文管理是 token 预算下的信息选择问题，不是简单截断。
- **边界**：摘要会丢细节，必须结构化保留用户偏好、硬约束和未完成事项；mock 测试稳定，但不能替代真实 API 冒烟。
**场景**：30 轮对话保留最近 6 轮 + 摘要 + 用户偏好；摘要只保留事实和约束，不保留寒暄。
**追问**：Q：摘要应该保留什么？A：硬约束、偏好、关键事实、未完成事项和下一步；不要保留客套和重复内容。

**任务关联**：配置/多模型 / 摘要与成本 / README / 3 分钟 demo
