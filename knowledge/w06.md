## 本周主线

- 用混合检索、rerank、query 改写补召回，用评测证明收益。

## Day 1 · BM25 与混合检索

**一句话**：向量检索擅长语义，BM25 擅长精确词；两者互补比二选一更稳。

**核心知识**

- BM25 基于词频、逆文档频率和文档长度归一化，对专有名词、编号、错误码很有效。
- 中文 BM25 需要分词；英文注意 stemming/停用词。
- 混合检索：dense + sparse 各自召回，再融合。
- RRF 按排名融合：`score = Σ 1/(k + rank)`，不需要分数归一化，稳健。
- 加权分数融合需要归一化和调权重，适合有标注数据时。

**速查**

```python
def rrf(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:
        for rank, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

**常见坑**

- 直接相加 BM25 分数和余弦分数，量纲不同，结果被某一路主导。
- 中文不分词就上 BM25，召回会很差。

**面试口述**

> BM25 为什么能补向量检索？RRF 相比加权融合有什么优缺点？

**深入理解**
- **机制**：BM25 用词频、IDF 和文档长度归一化打分；RRF 用排名融合多路召回，避免分数归一化。
- **边界**：中文不分词 BM25 效果差；RRF 丢失分数强弱；混合检索增加索引和延迟。
**场景**：错误码/产品型号/专有名词用 BM25 补召回，语义问题用 dense，RRF 融合。
**追问**：Q：RRF 的 k 怎么选？A：常用 60；k 越大排名差异越平滑，需用评测集调。

**任务关联**：BM25 索引 / hybrid / RRF / 对比表

## Day 2 · Rerank：用精度换延迟

**一句话**：先便宜地召回，再昂贵地精排。

**核心知识**

- bi-encoder 分别编码 query/doc，可预计算，适合召回；cross-encoder 联合编码，适合精排。
- rerank 放在召回之后：top 50–100 精排到 top 5–10。
- 候选越多质量可能越好，但延迟/成本线性增加。
- 常用模型：bge-reranker、Cohere Rerank；本地部署要注意显存和批处理。
- 评测要同时看 Recall@5、答案质量、P95 延迟。

**速查**

```text
召回 top 50 → rerank top 8 → 拼上下文 → 生成
```

**常见坑**

- 对全库做 cross-encoder，延迟不可接受。
- 只加 rerank 不建评测集，感觉变好但指标没升。

**面试口述**

> bi-encoder 和 cross-encoder 的区别？rerank 的延迟怎么控制？

**深入理解**
- **机制**：bi-encoder 分别编码 query/doc，可预计算；cross-encoder 联合编码，能建模细粒度交互。
- **边界**：rerank 只适合少量候选；候选越多延迟越高；模型领域不匹配会误排。
**场景**：召回 top 50，rerank top 8；按业务价值决定是否开启，高价值请求才精排。
**追问**：Q：rerank 提升不明显怎么办？A：先看召回是否已包含正确文档；没有召回，rerank 无从发挥。

**任务关联**：rerank 接入 / 消融表 / 延迟记录

## Day 3 · Query 改写：多查询、HyDE 与分解

**一句话**：用户的问题往往不是最好的检索 query。

**核心知识**

- query rewrite：补全指代、去掉口语噪声、提取关键词。
- multi-query：生成多个查询，分别召回后去重融合。
- HyDE：先生成假设答案，再用假设答案检索；适合短 query，但有幻觉偏移风险。
- 问题分解：多跳问题拆成子问题，分别检索再汇总。
- 改写会增加模型调用、延迟和成本；先看失败 query 类型再决定。

**速查**

```text
原 query：这个方案的成本怎么算？
改写 1：LLM 应用 token 成本估算方法
改写 2：RAG 单次问答成本 计算
```

**常见坑**

- 所有 query 都改写，简单问题被改复杂。
- HyDE 的假设答案编造了错误事实，检索被带偏。

**面试口述**

> HyDE 的原理和风险？什么场景适合用？

**深入理解**
- **机制**：query 改写补全指代、扩展同义词、分解多跳问题；HyDE 用假设答案做检索。
- **边界**：改写可能改变意图；HyDE 的假设答案可能幻觉；多查询增加成本和延迟。
**场景**：短 query/口语化问题先改写；多跳问题分解；简单问题不要过度改写。
**追问**：Q：什么时候不该用 query 改写？A：query 已经明确、延迟敏感、改写模型不可靠或成本高于收益时。

**任务关联**：3 种改写 / 10 个 query / 延迟成本对比

## Day 4 · Parent-child、上下文压缩与引用对齐

**一句话**：小块负责“找得准”，大块负责“读得懂”。

**核心知识**

- parent-child：子块检索，命中后返回父块；兼顾精度和上下文。
- sentence window：命中句子，扩展前后句；适合问答。
- 上下文压缩：摘要/抽取/去重，降低 token 和噪声，但可能压掉证据。
- 引用对齐：chunk id → 原文位置；尽量细到句子/页码。
- 存储要保留父子映射和原文，引用才能回溯。

**速查**

```text
child chunk 200–400 token（检索）
parent chunk 800–1500 token（生成）
```

**常见坑**

- 父块太大，把无关内容也塞给模型，成本上升。
- 压缩后引用指向的原文不在了，无法验证。

**面试口述**

> parent-child 切分解决什么问题？代价是什么？

**深入理解**
- **机制**：parent-child 用小块检索、父块生成；上下文压缩减少 token 和噪声。
- **边界**：父块太大会引入无关内容；压缩可能删掉关键证据；引用粒度会变粗。
**场景**：技术文档子块 300 token，父块 1000 token；引用定位到子块句子。
**追问**：Q：parent-child 的存储怎么设计？A：chunk 表存 parent_id，检索子块后 join 父块；原文位置单独存。

**任务关联**：父子块 / 引用定位 / 质量成本对比

## Day 5 · RAGAS 与评测体系

**一句话**：自动指标用来回归和筛坏例，最终判断仍要人工和业务指标。

**核心知识**

- faithfulness：答案是否忠于上下文。
- answer relevancy：答案是否切题。
- context precision：相关上下文是否排在前面。
- context recall：回答所需证据是否被召回。
- judge 有偏差，需人工校准；指标要跟业务目标绑定。

**速查**

```text
报告：数据集版本 / faithfulness / answer_relevancy /
      context_precision / context_recall / P95 / 成本
```

**常见坑**

- 把 RAGAS 分数当唯一真相，忽略人工抽检。
- 调参反复看同一评测集，造成过拟合。

**面试口述**

> RAGAS 指标能替代人工评测吗？为什么？

**深入理解**
- **机制**：RAGAS 用 LLM judge 计算 faithfulness、answer relevancy、context precision/recall。
- **边界**：judge 有偏差、成本高、对 prompt 敏感；指标之间可能冲突。
**场景**：每次改动跑同一评测集，人工抽检 10%，记录指标和失败类型。
**追问**：Q：RAGAS 分数下降但人工觉得更好，怎么办？A：检查 judge 偏差和评测集分布，不能只看自动分数。

**任务关联**：RAGAS 跑通 / 人工对比 / 不一致案例

## Day 6 · Lab：优化版 RAG 与消融

**一句话**：一次只改一个变量，才能知道是谁带来的提升。

**核心知识**

- 消融维度：切分、embedding、hybrid、rerank、rewrite、parent-child。
- 记录质量、延迟、成本三组指标，选满足 SLO 的组合。
- 默认配置不要堆满所有优化；保留开关，按场景切换。
- 失败案例比平均分更能指导下一步。

**速查**

```text
baseline: dense top5
+bm25: recall +?
+rerank: recall/faithfulness +?，P95 +?
+rewrite: 短 query recall +?，成本 +?
```

**常见坑**

- 一次改三个变量，无法归因。
- 只看离线指标，不看线上延迟和成本。

**面试口述**

> 你怎么证明一次 RAG 优化真的有效？

**深入理解**
- **机制**：消融实验一次只改一个变量，固定数据、模型、prompt 和评测集。
- **边界**：多变量同改无法归因；评测集太小波动大；离线指标不等于线上体验。
**场景**：baseline → +BM25 → +rerank → +rewrite，每组记录质量、P95、成本。
**追问**：Q：怎么选默认配置？A：在满足 SLO 的前提下，选质量/延迟/成本综合最优，并保留开关。

**任务关联**：组合实验 / 默认配置 / 消融报告 / 架构图

## Day 7 · 周复盘：高级检索

**一句话**：优化的终点不是“指标最高”，而是“在 SLO 下最合适”。

**核心知识**

- 能解释 hybrid、RRF、rerank、rewrite 的适用场景和代价。
- 能设计一组消融实验并解释结果。
- 能说清 RAGAS 四个指标的含义和局限。
- 能根据失败类型选择优化手段，而不是盲目加组件。

**速查**

```text
本周最小验收：
[ ] hybrid 有对比数据
[ ] rerank 有延迟数据
[ ] 至少 3 组消融
[ ] 能解释每组指标变化
[ ] 有默认配置和回滚开关
```

**常见坑**

- 优化组件越加越多，系统复杂到无法维护。
- 没有 baseline，面试时说不清“提升了多少”。

**面试口述**

> 用 3 分钟讲 RAG 优化的取舍。

**深入理解**
- **机制**：高级检索是“召回 + 排序 + 改写 + 上下文”的组合优化，不是组件堆叠。
- **边界**：每加一个组件都增加延迟、成本和维护复杂度；没有评测就无法证明收益。
**场景**：面试时给出 baseline、消融表、默认配置和回滚方案。
**追问**：Q：为什么不全开？A：可能超过延迟预算、增加故障面，且部分场景没有收益。

**任务关联**：W6 周测 / 消融结论 / 项目一需求 / 周报
