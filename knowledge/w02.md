## Day 1 · FastAPI 基础与分层

**一句话**：路由只负责协议，业务放 service，外部依赖通过依赖注入隔离。

**核心知识**

- FastAPI 用类型注解生成校验和 OpenAPI 文档；请求体/查询/路径参数都有明确来源。
- `Depends` 默认在**同一请求内**缓存依赖结果，适合数据库 session、当前用户等请求级资源。
- `lifespan` 管理启动/关闭资源（连接池、HTTP client），不要在每个请求里重复创建。
- 统一异常处理：业务异常映射成稳定错误码，不要把内部堆栈返回给客户端。
- 分层：router（协议）→ service（业务）→ repository/client（外部依赖）。

**速查**

```python
@router.post("/v1/chat")
async def chat(req: ChatRequest, svc: ChatService = Depends(get_chat_service)):
    return await svc.reply(req)
```

**常见坑**

- 在路由里直接写 SDK 调用，导致难测试、难复用；业务逻辑要能脱离 HTTP 运行。
- 在异步路由里调用阻塞库，会卡住整个事件循环；阻塞操作放线程池或改异步客户端。

**面试口述**

> FastAPI 的依赖注入和 Spring 的 DI 有什么异同？

**深入理解**
- **机制**：FastAPI 用依赖图解析参数，Depends 默认请求级缓存；lifespan 管理进程级资源，路由只做协议转换。
- **边界**：Depends 不是全局单例；在异步路由里调用阻塞库会卡事件循环；业务逻辑塞进 router 会难测试。
**场景**：数据库 session 用 yield dependency，每请求创建、请求结束关闭；service 不感知 HTTP。
**追问**：Q：测试时怎么替换依赖？A：用 app.dependency_overrides 覆盖 provider，测试结束清理。

**任务关联**：API 骨架 / service 分层 / 统一错误 / curl 示例

## Day 2 · Pydantic v2 与错误处理

**一句话**：用模型定义契约，把“不可信输入”挡在业务层之外。

**核心知识**

- `BaseModel` 做解析、类型转换和校验；`Field` 限制范围、长度、默认值。
- `field_validator` 校验单字段，`model_validator` 校验跨字段；分 before/after 模式。
- `model_config` 控制额外字段、别名、序列化；`pydantic-settings` 读环境变量。
- 校验失败 FastAPI 默认返回 422；业务错误用自定义异常 + 统一响应体。
- 响应模型要显式声明，避免把内部字段（密码、token）意外返回。

**速查**

```python
class ChatRequest(BaseModel):
    message: str = Field(min_length=1, max_length=8000)
    max_tokens: int = Field(default=1024, ge=1, le=8192)

    @field_validator("message")
    @classmethod
    def not_blank(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("message 不能为空")
        return v.strip()
```

**常见坑**

- 只做前端校验，不做后端校验；API 可以被任意客户端直接调用。
- 错误响应格式一会一个样，客户端无法稳定处理；错误码要版本化、可机读。

**面试口述**

> field validator 和 model validator 的区别？什么时候用哪个？

**深入理解**
- **机制**：Pydantic 先解析再校验，field validator 管单字段，model validator 管跨字段；response_model 控制输出白名单。
- **边界**：校验失败默认 422，不要和业务 400 混用；extra 字段是否允许要显式配置；strict 模式会改变类型转换行为。
**场景**：max_tokens 限制在 1–8192；role 用枚举；错误响应统一 code/message/request_id。
**追问**：Q：field validator 和 model validator 怎么选？A：单字段约束用 field，跨字段/整模型用 model；都分 before/after。

**任务关联**：ChatRequest / 错误码表 / 15 个校验测试

## Day 3 · 持久化：会话与消息

**一句话**：存全量消息，发给模型时只取需要的部分。

**核心知识**

- SQLAlchemy 2.0 用 `AsyncSession`；session 不是并发安全的，按请求/任务创建。
- 表：`conversations`（会话）与 `messages`（消息），外键 + 索引；软删除保留审计。
- 消息表存 role/content/token/model/latency/created_at，支持成本、审计、重放。
- 事务边界放在 service：一次业务操作要么全成功，要么回滚。
- 上下文裁剪策略：最近 N 轮 + 摘要 + 与当前问题相关的历史。

**速查**

```sql
CREATE INDEX idx_messages_conv_created
ON messages (conversation_id, created_at DESC);
```

**常见坑**

- 把完整历史每轮都塞回模型，token 成本会指数级增长。
- 在多个协程间共享同一个 AsyncSession，会出现事务串线/连接错误。

**面试口述**

> 为什么消息表要存 token、模型和耗时？除了“以后可能有用”还有什么价值？

**深入理解**
- **机制**：AsyncSession 绑定连接和事务上下文；repository 封装查询，service 控制事务边界。
- **边界**：Session 不能跨并发任务共享；懒加载在异步下可能报错；深分页 offset 会越来越慢。
**场景**：会话列表按 updated_at 倒序，消息分页用 cursor（created_at + id）而不是大 offset。
**追问**：Q：offset 和 cursor 分页怎么选？A：后台小数据可用 offset；面向用户、数据量大、要求稳定用 cursor。

**任务关联**：conversations/messages / 历史查询 / ER 图 / 索引

## Day 4 · SSE 流式与韧性

**一句话**：流式不是“把响应写出去”，而是处理断连、超时、上游失败和背压。

**核心知识**

- `StreamingResponse` + `text/event-stream`；每个事件以空行结束，客户端用 EventSource/fetch 读取。
- 客户端断开要捕获取消信号，取消上游请求、释放连接、记录部分 usage。
- 代理/网关默认可能缓冲响应，必须关闭 buffering，否则“流式”变一次性。
- 429 用退避 + 抖动，尊重 `Retry-After`；5xx 有限重试；401 不重试。
- 每个请求带 request id，日志、trace、错误响应统一关联。

**速查**

```python
async def event_stream():
    try:
        async for token in upstream():
            yield f"data: {json.dumps({'delta': token})}\n\n"
        yield "data: [DONE]\n\n"
    except asyncio.CancelledError:
        await close_upstream()
        raise
```

**常见坑**

- 断连后后台还继续生成，既浪费成本又可能写脏数据。
- 把 SSE 当成 WebSocket 用，试图客户端→服务端双向通信。

**面试口述**

> 客户端断开流式连接时，服务端应该做哪些清理？

**深入理解**
- **机制**：SSE 是长连接上的事件流；StreamingResponse 逐块写出，客户端断开通过取消信号向上游传播。
- **边界**：没有心跳的连接可能被中间层断开；代理缓冲会把流式变成一次性；客户端断开后继续生成会浪费成本。
**场景**：先发 meta 事件（引用/模型），再发 delta，最后发 done；记录首 token 和总耗时。
**追问**：Q：怎么测试流式接口？A：httpx stream 读取多块，断言事件顺序、[DONE]、断连清理和错误事件。

**任务关联**：/chat/stream / 断连处理 / 首 token 延迟 / EventSource 验证

## Day 5 · 测试、Docker 与交付

**一句话**：新机器能一键启动，才算真正的交付。

**核心知识**

- pytest + httpx `AsyncClient` 测 API；依赖覆盖替换数据库/上游，保证测试稳定。
- 覆盖正常、校验失败、上游错误、流式、断连五类路径。
- Docker 多阶段构建：构建阶段装依赖，运行阶段只拷产物；用 slim 镜像。
- 非 root 运行、`.dockerignore`、健康检查、环境变量注入密钥。
- README 写清启动命令、环境变量、健康检查、已知限制。

**速查**

```dockerfile
FROM python:3.12-slim AS runtime
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
USER 10001
CMD ["/app/.venv/bin/uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**常见坑**

- 镜像里包含 `.env`、测试数据、Git 历史；用 .dockerignore 和最小上下文。
- 只测 healthcheck，不测真实业务链路；上线后才发现参数校验/流式有问题。

**面试口述**

> Docker 镜像怎么减小？多阶段构建具体省掉了什么？

**深入理解**
- **机制**：多阶段构建把编译依赖和运行时分离；健康检查让编排系统知道服务是否真正可用。
- **边界**：镜像越小不一定启动越快；构建缓存会影响层复用；密钥不能进入镜像层。
**场景**：compose 中 api 依赖 postgres healthy；启动时跑 migration，失败快速退出。
**追问**：Q：Testcontainers 和 mock 怎么选？A：集成/契约测试用 Testcontainers，单元测试用 mock；两者都要有。

**任务关联**：API 测试 / Dockerfile / compose / 镜像大小记录

## Day 6 · Lab：流式对话 API 完整版

**一句话**：并发流式最怕共享可变状态；隔离、限流、可观测是三件套。

**核心知识**

- 每个请求独立上下文/生成器，不共享 buffer；request id 贯穿日志和响应。
- 限流保护上游配额和成本；按用户/租户/模型维度分别限。
- 压测看首 token、P95、错误率、并发连接，不只看 QPS。
- 连接池大小、上游配额、数据库连接数通常先成为瓶颈。
- 优雅关闭：停止接收新请求，等待进行中的流结束或超时。

**速查**

```text
压测记录模板：
并发 20 / 时长 3min / 成功率 / P50 首token / P95 首token / P95 总时长 / 错误码分布
```

**常见坑**

- 20 路并发不串消息的前提是“无共享可变 buffer”，不是加锁就能解决。
- 压测只打 healthcheck，没覆盖真实模型调用，数据没有意义。

**面试口述**

> 20 路并发流式请求，怎么保证不串消息？

**深入理解**
- **机制**：每个流式请求需要独立上下文和生成器；限流保护上游配额，连接池限制数据库并发。
- **边界**：共享可变 buffer 会串消息；连接池耗尽会让请求排队；上游 429 会放大延迟。
**场景**：20 路并发流式请求，记录首 token、P95、错误率和消息隔离。
**追问**：Q：为什么只看平均延迟不够？A：平均值掩盖长尾；流式体验由 P95/P99 和错误率决定。

**任务关联**：会话管理 / 限流 / 20 并发压测 / 架构图

## Day 7 · 周复盘：FastAPI 与 AI 服务

**一句话**：服务化能力 = 协议 + 校验 + 持久化 + 韧性 + 可交付。

**核心知识**

- 复盘 API 的五个边界：输入、输出、超时、错误、权限。
- 能画出请求生命周期：网关 → 路由 → 依赖 → service → 上游 → 持久化 → 流式返回。
- 能解释一次 429/断连/上游超时的完整处理链路。
- 能说清 Docker 镜像里有什么、密钥从哪里来。

**速查**

```text
本周最小验收：
[ ] docker compose up 一键启动
[ ] OpenAPI 文档完整
[ ] 20 并发流式不串消息
[ ] 测试覆盖错误与断连
[ ] 能讲 2 分钟架构
```

**常见坑**

- 只关注“接口能返回”，忽略超时、重试、限流，线上会被上游拖死。
- 把配置写死在代码里，换环境就要改代码。

**面试口述**

> 用 2 分钟讲 chat-api 的架构、并发模型和故障处理。

**深入理解**
- **机制**：SLO 是可用性和延迟的目标，错误预算决定什么时候该停止加功能、先修稳定性。
- **边界**：只测 happy path 会漏掉真实故障；日志里打印完整文档/用户输入有合规风险。
**场景**：上游 429 持续 5 分钟，触发限流、降级和告警；记录降级原因和影响范围。
**追问**：Q：一次请求至少记录什么？A：request id、租户、模型、token、首 token/总延迟、错误码、是否降级。

**任务关联**：W2 周测 / 代码重构 / 周报 / tag v0.2
