## 本周主线

- 建立“Prompt → RAG → Fine-tune”的决策树。
- 跑通一次 LoRA/QLoRA，理解数据、超参和显存。
- 用评测判断微调是否值得，而不是只看 loss。

## Day 1 · 微调决策树

**一句话**：知识频繁变化用 RAG，风格/格式固定才考虑微调。

**核心知识**

- Prompt：先解决 80% 问题，成本最低、迭代最快。
- RAG：动态知识、需要引用/权限、可追溯。
- Fine-tune：固定风格/格式/领域语言、有高质量标注数据、需要小模型降本。
- 微调不适合注入频繁变化的事实；会过时且难追溯。
- 微调有维护成本：数据、训练、评测、版本、回滚。

**速查**

```text
决策顺序：
Prompt 能解决？→ 是：先用
需要外部知识/引用？→ 是：RAG
需要固定风格/格式且有数据？→ 是：微调
```

**常见坑**

- 一上来就微调，数据不够、评测没有，最后不如 Prompt。
- 用微调记事实，知识更新后要反复重训。

**面试口述**

> 什么时候用 RAG，什么时候用微调？两者能叠加吗？

**深入理解**
- **机制**：Prompt 解决表达，RAG 解决知识，微调解决风格/格式/领域模式；三者可叠加。
- **边界**：频繁变化的事实不适合微调；数据不足/质量差时微调会放大问题；微调有版本和维护成本。
**场景**：企业知识库先用 RAG；输出格式不稳定再考虑 SFT；最后才评估微调。
**追问**：Q：RAG 和微调能一起用吗？A：能；RAG 提供证据，微调固定风格/格式，注意评测和版本。

**任务关联**：决策树 / 5 个案例 / 不该微调的案例

## Day 2 · 数据工程：业务数据变训练样本

**一句话**：数据质量决定上限，训练技巧只能逼近上限。

**核心知识**

- 格式：instruction/input/output 或 chat messages；训练和推理模板要一致。
- chat template：角色标记、特殊 token、loss mask 必须匹配。
- 清洗：去重、去噪、长度控制、答案审核、隐私脱敏。
- 划分：train/validation/test 隔离，防止泄漏。
- 数据卡：来源、规模、字段、清洗、许可、隐私。

**速查**

```json
{"messages": [
  {"role": "system", "content": "你是企业知识库助手"},
  {"role": "user", "content": "..."},
  {"role": "assistant", "content": "..."}
]}
```

**常见坑**

- 训练用一套模板，推理用另一套，loss 正常但效果差。
- 测试集和训练集重复，评测分数虚高。

**面试口述**

> 训练数据的质量怎么保证？chat template 为什么重要？

**深入理解**
- **机制**：训练数据要套 chat template、mask 掉非 assistant 部分；训练和推理模板必须一致。
- **边界**：模板错会导致 loss 正常但效果差；数据泄漏会让评测虚高；隐私数据要脱敏。
**场景**：50 条业务问答转 messages，去重、长度统计、人工审核，划 train/val/test。
**追问**：Q：怎么发现模板错？A：打印 token、对比推理 prompt、检查 loss mask 和特殊 token。

**任务关联**：50 条样本 / 数据卡 / 去重 / 长度统计

## Day 3 · LoRA/QLoRA 原理与超参

**一句话**：LoRA 冻结基座，只训练低秩适配器，用少量参数换领域能力。

**核心知识**

- LoRA：`W' = W + BA`，A/B 低秩；只训练 A/B，冻结原权重。
- rank 越大容量越强，但更易过拟合、显存更高；常用 8–64。
- alpha 常设为 rank 的 1–2 倍；dropout 防过拟合。
- QLoRA：4-bit 量化基座 + LoRA，进一步降显存，速度/质量需权衡。
- 目标模块通常选 attention 的 q/k/v/o，也可加 FFN。

**速查**

```python
LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    task_type="CAUSAL_LM",
)
```

**常见坑**

- rank 盲目调大，数据少时直接过拟合。
- 只训练 adapter 但保存/加载方式不对，推理没生效。

**面试口述**

> LoRA 为什么省显存？rank 怎么选？

**深入理解**
- **机制**：LoRA 冻结基座，训练低秩 A/B 矩阵；rank 控制容量，alpha 控制缩放。
- **边界**：rank 越大越易过拟合、显存越高；目标模块选错效果差；adapter 保存/加载要匹配。
**场景**：1.5B 模型，r=16，alpha=32，q/k/v/o 目标模块，先跑 1–2 epoch。
**追问**：Q：QLoRA 和 LoRA 怎么选？A：显存不够用 QLoRA；够用优先 LoRA，速度和质量更稳。

**任务关联**：LoRA 配置 / 参数量对比 / 原理笔记

## Day 4 · 训练实战

**一句话**：先跑通小模型，再谈效果；先控制变量，再调参。

**核心知识**

- 关键参数：learning rate、epoch、batch size、grad accumulation、warmup、weight decay。
- 显存：模型权重 + 梯度 + 优化器状态 + 激活 + KV cache；QLoRA 主要省权重。
- 监控：loss、验证集指标、显存、吞吐、梯度范数。
- 保存：adapter、tokenizer、训练配置、数据版本。
- 推理：加载基座 + adapter，模板/参数与训练一致。

**速查**

```text
推荐起步：lr 1e-4 ~ 2e-4，epoch 1–3，batch 1 + grad_accum 8
先跑 50 步确认 loss 下降，再扩大训练
```

**常见坑**

- 只看 training loss，不看验证集和人工样例。
- 学习率过大导致 loss 爆炸/灾难性遗忘。

**面试口述**

> 训练 loss 下降但效果变差，可能是什么原因？

**深入理解**
- **机制**：训练是数据、模板、超参、显存和评测的共同作用；loss 只是优化目标。
- **边界**：loss 下降可能过拟合；学习率过大会崩；训练/推理不一致会白训。
**场景**：Colab 小模型跑 1–2 epoch，记录 loss、显存、时长和生成样例。
**追问**：Q：loss 正常但效果差，先查什么？A：模板、label mask、数据质量、推理参数和验证集分布。

**任务关联**：Colab 训练 / loss 曲线 / 显存记录 / 3 个样例

## Day 5 · 微调评测：对比 Prompt 基线

**一句话**：微调不是免费午餐，要用同一评测集证明值得。

**核心知识**

- 对比：base / prompt / RAG / LoRA，固定评测集和解码参数。
- 指标：任务准确率、格式合法率、人工质量、延迟、显存、成本。
- 灾难性遗忘：在通用能力集上回归，和基座对比。
- 过拟合：验证集早停、数据增强、降低 rank/epoch。
- 结论要明确：是否上线、什么场景用、维护成本多少。

**速查**

```text
对比表：方案 / 质量 / 延迟 / 显存 / 成本 / 维护成本 / 结论
```

**常见坑**

- 微调后只在训练分布上测，换个问法就崩。
- 不记录训练配置和数据版本，结果无法复现。

**面试口述**

> 微调后怎么判断有没有灾难性遗忘？

**深入理解**
- **机制**：微调评测要和 Prompt/RAG 基线对比，固定评测集、解码参数和评测脚本。
- **边界**：只在训练分布上测会虚高；通用能力退化是灾难性遗忘；维护成本要算。
**场景**：base / prompt / LoRA 三组对比，记录质量、延迟、显存和成本。
**追问**：Q：怎么检测灾难性遗忘？A：在通用能力集回归，和基座对比，人工抽检多样输入。

**任务关联**：20 条测试 / base vs prompt vs LoRA / 对比报告

## Day 6 · Lab：小模型微调与对比

**一句话**：一次可复现的实验，比十个“跑通了”的截图有价值。

**核心知识**

- 固定 seed、数据版本、代码 commit、超参、环境。
- 跑 3 组配置（rank/lr/epoch）对比，选最优。
- 保存 adapter、日志、评测脚本、失败案例。
- 报告结构：任务/数据 → 基线 → 配置 → 结果 → 结论 → 限制。
- 面试时能现场解释每个参数为什么这么选。

**速查**

```text
实验记录：
data=v1 / base=Qwen2.5-0.5B / r=16 / lr=2e-4 / epoch=2 /
eval=20 条 / acc=0.78 / 显存=8.2GB / 训练=35min
```

**常见坑**

- 不固定 seed，结果每次都不一样，无法比较。
- 只保存最终模型，不保存数据/配置，无法复现。

**面试口述**

> 用 3 分钟讲你的微调实验。

**深入理解**
- **机制**：可复现实验需要数据版本、代码 commit、超参、seed、环境和评测脚本。
- **边界**：不固定 seed 无法比较；只保存最终模型无法复现；数据泄漏会让结论错误。
**场景**：3 组 rank/lr/epoch 对比，保存 adapter、日志、评测结果和失败案例。
**追问**：Q：怎么保证实验可复现？A：固定 seed/环境，记录数据 hash 和配置，脚本一键跑。

**任务关联**：可复现脚本 / 3 组配置 / 实验报告 / 失败案例

## Day 7 · 周复盘：微调与数据

**一句话**：能说“不该微调”比会微调更加分。

**核心知识**

- 能画 Prompt/RAG/Fine-tune 决策树。
- 能解释 LoRA/QLoRA、rank/alpha、显存构成。
- 能说清数据模板、loss mask、灾难性遗忘。
- 能用评测证明微调是否值得。

**速查**

```text
本周最小验收：
[ ] 决策树能讲
[ ] LoRA 实验可复现
[ ] 有 base vs prompt vs LoRA 对比
[ ] 能解释 3 个失败原因
[ ] 能说“不该微调”的场景
```

**常见坑**

- 把微调当万能药，忽略数据和维护成本。
- 只讲训练，不讲评测和回滚。

**面试口述**

> 什么情况下你会建议不做微调？

**深入理解**
- **机制**：微调决策树：Prompt → RAG → 微调；能不用微调就不微调。
- **边界**：知识频繁变化、数据不足、需要引用/权限时不适合微调；维护成本常被低估。
**场景**：面试时给出“不该微调”的案例，比只会训练更加分。
**追问**：Q：什么情况下建议不做微调？A：Prompt/RAG 已达标、数据质量差、团队无维护能力时。
