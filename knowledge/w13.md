## Day 1 · vLLM 与推理服务

**一句话**：推理服务的核心指标是吞吐、首 token、显存，不是参数量。

**核心知识**

- PagedAttention 把 KV cache 分页管理，减少碎片，提高并发。
- 连续批处理动态合并请求，减少 GPU 空等。
- 关键参数：`max-model-len`、`gpu-memory-utilization`、`max-num-seqs`、张量并行。
- OpenAI 兼容 API 方便接入现有客户端。
- 部署要监控：吞吐、P95、显存、排队长度、错误率。

**速查**

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --port 8000
```

**常见坑**

- 上下文开太大，KV cache 吃满显存，并发骤降。
- 只看单请求延迟，不看并发吞吐。

**面试口述**

> vLLM 为什么吞吐高？代价是什么？

**任务关联**：本地推理 / 20 请求 / 吞吐/显存记录 / 生命周期图

## Day 2 · 量化与性能三角

**一句话**：量化省显存、提吞吐，但必须用业务样本验证质量。

**核心知识**

- FP16 → INT8/INT4：权重/激活精度下降，显存降低，吞吐提升。
- AWQ/GPTQ 是常见权重量化方法；KV cache 也可量化。
- 质量损失在长尾/推理/代码任务上更明显。
- 量化需要校准数据；校准分布和业务不一致会掉点。
- 选型看质量、显存、吞吐、硬件/算子兼容。

**速查**

```text
对比表：精度 / 显存 / 吞吐 / 质量 / 兼容性
结论：在满足质量门槛下，选最省显存的配置
```

**常见坑**

- 只看 perplexity，不看业务评测集。
- 量化后推理参数/模板没变，误以为是模型质量问题。

**面试口述**

> 量化的收益和风险是什么？怎么验证质量？

**任务关联**：量化对比 / 质量样例 / 三角权衡表

## Day 3 · Spring AI 基础

**一句话**：Java 不是包袱；企业集成、权限、事务和运维才是 AI 落地的稀缺能力。

**核心知识**

- `ChatClient` 提供 fluent API：prompt、stream、structured output、advisors。
- PromptTemplate 管理变量；Advisor 做 RAG、日志、护栏等横切逻辑。
- 流式用 `Flux<String>` / SSE，注意背压和超时。
- 结构化输出用 JSON schema/实体映射，仍要应用侧校验。
- Spring AI 适合把 AI 接进现有 Spring 微服务体系。

**速查**

```java
String answer = chatClient.prompt()
    .system("只依据上下文回答")
    .user(question)
    .call()
    .content();
```

**常见坑**

- 为了“统一语言”把所有 AI 逻辑塞进 Java，牺牲实验效率。
- 不做超时/降级，模型供应商故障拖垮主站。

**面试口述**

> 为什么用 Spring AI 而不是再写一个 Python 服务？边界怎么划？

**任务关联**：Spring AI 服务 / 流式 SSE / 结构化输出 / 对比笔记

## Day 4 · Spring AI RAG 与模型网关

**一句话**：把模型供应商当不可靠下游治理，和微服务网关思路一致。

**核心知识**

- RAG：VectorStore/Retriever + Advisor；引用、权限、租户过滤仍要自己做。
- 模型网关：统一协议、鉴权、配额、路由、熔断、降级、计量。
- 路由维度：任务类型、质量、成本、延迟、可用性。
- 降级：备用模型/小模型/缓存答案；记录降级原因。
- 灰度：按租户/比例分流，监控质量与成本。

**速查**

```text
请求 → 鉴权/配额 → 路由 → RAG → 模型 → 校验 → 计量
                         ↘ 故障 → 备用模型/缓存 → 降级标记
```

**常见坑**

- 路由没有可解释原因，线上无法排障。
- 降级后不记录，用户得到低质量答案却无人知晓。

**面试口述**

> 多模型路由策略怎么设计？如何做灰度？

**任务关联**：RAG + 路由 / 两家供应商 / 降级 / 架构图

## Day 5 · Java 生产化：SSE、背压、熔断、指标

**一句话**：Java 候选人的杀手锏是工程化，不是会调 API。

**核心知识**

- WebFlux `Flux<ServerSentEvent>` 做流式；限制缓冲，按下游消费。
- 客户端断开时取消上游，释放连接。
- Resilience4j：超时、重试、熔断、限流、舱壁。
- Micrometer 采集延迟、错误、token/调用计数，接 Prometheus。
- 缓存：精确/语义缓存要带租户和版本。

**速查**

```java
Flux<ServerSentEvent<String>> stream =
    chatClient.prompt().user(q).stream().content()
        .map(t -> ServerSentEvent.builder(t).build())
        .timeout(Duration.ofSeconds(60));
```

**常见坑**

- 无界缓冲导致 OOM；流式一定要背压。
- 熔断只包模型调用，没包检索/DB，整体仍会挂。

**面试口述**

> WebFlux 下流式返回怎么处理背压和超时？

**任务关联**：超时/熔断/缓存 / 指标 / 100/200 并发压测

## Day 6 · Lab：项目三完整版

**一句话**：项目三证明“你能把 AI 接进企业系统”，不是“你会写 Python”。

**核心知识**

- 功能：模型网关 + RAG + 流式 + 降级 + 缓存 + 监控。
- 权限：复用现有鉴权/租户/审计，不另起一套。
- 指标：可用性、P95、缓存命中、单次成本。
- 成本表：输入/输出 token、检索、rerank、缓存节省。
- 边界：Python 负责实验/Agent，Java 负责企业集成/稳定性的场景。

**速查**

```text
项目三 demo：
1. 正常 RAG 问答（流式+引用）
2. 主供应商故障 → 自动降级
3. 缓存命中 → 延迟/成本下降
4. 压测指标与成本表
```

**常见坑**

- 只做“调用模型”，没有网关/降级/监控，和项目一重复。
- 压测数据没有环境说明，不可信。

**面试口述**

> 用 10 分钟讲项目三，和项目一的区别是什么？

**任务关联**：完整服务 / 压测 / 成本表 / README / 视频
