# W09 · Agent 基础与工具调用

> 阶段：Agent 工程（P3）｜Day 1–7
> 用法：先读当天小节，再去做学习舱任务；做完回来补“常见坑”。

## 本周主线

- 先判断“该不该用 Agent”，再手写一个可观测的 Agent 内核。
- 理解 ReAct、工具协议、记忆、护栏和成本。
- 不用框架也能讲清循环、状态、错误处理。

## Day 1 · Agent 的适用边界

**一句话**：能不用 Agent 就不用；路径不确定、需要工具组合时再上。

**核心知识**

- workflow：控制流由代码预先定义，可预测、易测试、易审计。
- agent：由模型决定下一步，灵活但非确定性、成本高、难调试。
- 适合 Agent：开放式研究、多工具组合、路径不确定、需要根据中间结果调整。
- 不适合：步骤固定、合规高风险、强可解释、成本/延迟敏感、副作用大且难回滚。
- 设计顺序：先 workflow，再单 Agent，最后才多 Agent。

**速查**

```text
决策树：
步骤固定？→ workflow
需要动态选工具？→ 单 Agent
需要并行/不同权限分工？→ 多 Agent
```

**常见坑**

- 为了“看起来高级”上 Agent，结果比 workflow 更慢更贵更不稳。
- 没有成功标准和任务集，无法判断 Agent 是否有用。

**面试口述**

> 什么时候不该用 Agent？你会怎么判断？

**深入理解**
- **机制**：workflow 的控制流由代码定义，agent 由模型动态决定下一步；前者可预测，后者灵活。
- **边界**：合规高风险、步骤固定、成本敏感时优先 workflow；agent 增加不确定性和调试成本。
**场景**：客服工单分类用 workflow；开放式研究/多工具组合才用 agent。
**追问**：Q：怎么判断该不该用 agent？A：先问路径是否确定、是否需要动态工具、失败代价是否可接受。

**任务关联**：3 个场景判断 / Agent ADR / 架构图

## Day 2 · 手写 ReAct 循环

**一句话**：ReAct 是“思考 → 行动 → 观察”的循环，不是让模型自由发挥。

**核心知识**

- 每轮：模型输出 thought/action，应用执行工具，把 observation 回填。
- 需要停止条件：完成信号、最大步数、预算耗尽、连续失败。
- 解析动作要健壮：JSON/函数调用优先，避免正则解析自由文本。
- 观察结果要截断/结构化，避免把超长网页塞回上下文。
- 全链路 trace：每步输入、工具、参数、结果、耗时、token。

**速查**

```python
for step in range(MAX_STEPS):
    action = model.decide(state)
    if action.type == "final":
        return action.answer
    observation = tools[action.name](**action.args)
    state.append(observation)
```

**常见坑**

- 没有最大步数，模型可以无限循环。
- 工具报错直接抛异常，Agent 直接崩；应返回结构化错误让模型决策。

**面试口述**

> ReAct 循环的核心风险有哪些？你怎么止损？

**深入理解**
- **机制**：ReAct 循环是 thought → action → observation；应用执行工具并把结果回填。
- **边界**：没有最大步数会死循环；工具错误直接抛异常会中断；观察结果可能被注入。
**场景**：每步记录 trace，设最大步数/预算/重复动作检测；失败返回结构化错误。
**追问**：Q：怎么检测死循环？A：工具+参数哈希重复、步数上限、状态无变化、连续相同 observation。

**任务关联**：mini-agent / 3 个 mock 工具 / 10 条 trace

## Day 3 · 工具设计、参数校验与幂等

**一句话**：工具是 Agent 的手，手要有权限、有边界、有痛觉。

**核心知识**

- 工具名动词化，描述写清“何时用/何时不用”，参数用 JSON Schema。
- 服务端校验参数：类型、枚举、范围、白名单；不要只信模型输出。
- 错误结构化：错误类型、原因、是否可重试、建议动作。
- 有副作用的工具要幂等：幂等 key、去重表、事务。
- 高风险工具加审批、超时、沙箱、审计。

**速查**

```json
{
  "name": "query_orders",
  "description": "按用户 ID 查询订单；只读，最多返回 20 条",
  "parameters": {
    "type": "object",
    "properties": {"user_id": {"type": "string"}, "limit": {"type": "integer", "maximum": 20}},
    "required": ["user_id"]
  }
}
```

**常见坑**

- SQL 工具给读写权限，模型一句 DROP 就出事。
- 重试“发通知”没有幂等，用户收到多条。

**面试口述**

> 怎么防止工具参数注入？权限应该放在哪一层？

**深入理解**
- **机制**：工具是带 schema 的函数；模型只生成调用意图，应用负责校验、权限、执行和错误处理。
- **边界**：描述不清会选错工具；参数不校验会注入；有副作用的工具重试要幂等。
**场景**：SQL 工具只读、白名单、参数化、行级权限、超时和行数限制。
**追问**：Q：工具描述怎么写？A：动词化名称、何时用/不用、参数类型/枚举/示例、错误和权限边界。

**任务关联**：5 个工具 / Pydantic 校验 / 幂等 / 正确率

## Day 4 · Memory：短期、长期与遗忘

**一句话**：记忆不是越多越好，错误记忆比没有记忆更糟。

**核心知识**

- 短期记忆：当前会话消息，按 token 预算裁剪。
- 长期记忆：用户偏好、稳定事实、任务结果；要有来源、置信度、时间。
- 写入策略：只写明确、稳定、可验证的信息；不要每轮都写。
- 检索策略：按当前任务检索相关记忆，避免全量注入。
- 遗忘/删除：过期、纠错、用户撤回；敏感信息不写或加密。

**速查**

```text
记忆条目：content / source / confidence / created_at / expires_at / tenant
```

**常见坑**

- 把模型推断写入长期记忆，后续一直被错误前提带偏。
- 没有删除入口，用户无法纠正隐私信息。

**面试口述**

> 记忆什么时候写？写错了怎么办？

**深入理解**
- **机制**：短期记忆是会话上下文，长期记忆是跨会话的偏好/事实；都需要写入、检索、更新和删除策略。
- **边界**：每轮都写会污染；模型推断不是事实；敏感信息不能随便存。
**场景**：只记录用户明确偏好和任务结果，带来源/置信度/过期时间，提供查看和删除。
**追问**：Q：记忆冲突怎么办？A：以最新明确指令为准，保留来源和时间，允许用户纠正/删除。

**任务关联**：会话摘要 / 偏好存储 / 删除 / 隐私风险

## Day 5 · Guardrails、预算与红队

**一句话**：Agent 一定要有刹车，尤其是能花钱、能写数据的工具。

**核心知识**

- 预算：最大步数、最大 token/金额、最大时间；超限降级。
- 工具权限：白名单、最小权限、审批、沙箱。
- 输入/输出护栏：敏感信息、注入、格式、越权。
- 重复动作检测：相同工具+参数哈希，避免死循环。
- Kill switch：异常时立即停止，保留现场 trace。

**速查**

```text
预算示例：max_steps=8 / max_tokens=30k / max_cost=0.5 元 / timeout=120s
```

**常见坑**

- 只限步数不限 token，单步超长上下文仍能烧钱。
- 审批只做“通过”，没有拒绝/修改/超时分支。

**面试口述**

> Agent 的预算怎么设？超预算后怎么降级？

**深入理解**
- **机制**：护栏是纵深防御：输入校验、工具权限、预算、审批、输出过滤和 kill switch。
- **边界**：只限步数不限 token 仍会烧钱；审批只有“通过”没有拒绝等于没审批。
**场景**：高风险工具前暂停，超预算降级，异常时立即停止并保留 trace。
**追问**：Q：预算怎么设？A：按任务价值设最大步数/token/金额/时间，超限给当前结论和待办。

**任务关联**：步数/预算 / 审批 / 重复检测 / 10 条红队

## Day 6 · Lab：mini-agent 完整版

**一句话**：先手写，再用框架；否则你不知道框架帮你做了什么。

**核心知识**

- 组件：模型适配器、工具注册表、循环、状态、记忆、trace、护栏。
- 工具注册表统一 schema、执行、错误、超时、权限。
- 状态要可序列化，方便恢复和回放。
- 评测：任务成功率、平均步数、工具错误率、人工干预率。
- 保留手写版，面试时能讲底层。

**速查**

```text
agent/
├─ loop.py
├─ tools/
├─ memory.py
├─ trace.py
└─ eval.py
```

**常见坑**

- 把所有逻辑塞进一个 prompt，没有可测试的代码结构。
- 没有 trace，失败后无法复盘。

**面试口述**

> 手写 Agent 和 LangGraph 的区别？什么时候用框架？

**深入理解**
- **机制**：mini-agent 包含模型适配、工具注册、循环、状态、记忆、trace 和护栏。
- **边界**：全塞进 prompt 无法测试；没有 trace 无法复盘；没有任务集无法证明成功率。
**场景**：3 个工具 + 10 条任务，记录成功率、步数、工具错误率和成本。
**追问**：Q：手写和框架怎么选？A：简单任务手写更可控；复杂状态/审批/恢复用 LangGraph。

**任务关联**：mini-agent / 10 条任务评测 / README / demo

## Day 7 · 周复盘：Agent 基础

**一句话**：Agent 的难点不是“让它动”，是“让它停”和“让它可控”。

**核心知识**

- 能判断 workflow vs agent。
- 能画 ReAct 循环并标出失败点。
- 能设计工具 schema、错误协议、幂等和权限。
- 能说清记忆写入/删除策略和预算控制。

**速查**

```text
本周最小验收：
[ ] 手写循环可跑
[ ] 3 个工具可调用
[ ] 工具报错可恢复
[ ] 有最大步数/预算
[ ] 有完整 trace
```

**常见坑**

- 只追求“多智能体”，单 Agent 还没跑稳。
- 没有任务集，无法证明成功率。

**面试口述**

> 用 3 分钟讲 Agent 的组成和失败模式。

**深入理解**
- **机制**：Agent 的难点是停止条件、工具边界、权限和可观测性，不是“让模型自由发挥”。
- **边界**：没有成功标准就无法评测；多智能体不是默认答案。
**场景**：面试时画循环图，标出死循环、工具误用、注入和成本失控四个失败点。
**追问**：Q：怎么证明 agent 可靠？A：固定任务集、多次运行分布、人工抽检和失败分类。

**任务关联**：W9 周测 / 循环图 / GitHub 仓库 / 周报
