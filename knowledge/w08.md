## Day 1 · Docker Compose 与配置管理

**一句话**：新机器 10 分钟内能跑起来，才算可交付。

**核心知识**

- Compose 编排 api、postgres、redis、可选 langfuse；服务名即 DNS。
- 数据卷持久化数据库；healthcheck 判断就绪；depends_on 配 condition。
- 配置走环境变量；`.env.example` 提供模板，绝不提交真实密钥。
- 启动时跑 migration；失败要快速退出，不要带病启动。
- 只暴露必要端口；生产用反向代理和 TLS。

**速查**

```yaml
services:
  api:
    build: .
    env_file: .env
    depends_on:
      postgres: { condition: service_healthy }
    ports: ["8000:8000"]
```

**常见坑**

- 容器启动顺序靠 sleep，数据库没就绪就迁移失败。
- 镜像里打包 `.env`，密钥泄露。

**面试口述**

> Compose 的网络、卷和健康检查怎么设计？

**深入理解**
- **机制**：Compose 用服务名做 DNS，卷持久化数据，healthcheck 让依赖方等待就绪。
- **边界**：depends_on 不等于健康；migration 失败要快速退出；密钥不能进镜像。
**场景**：新机器 clone 后 docker compose up，10 分钟内可访问；启动时间写入 README。
**追问**：Q：启动顺序怎么保证？A：healthcheck + depends_on condition；应用内重试连接，不要只靠 sleep。

**任务关联**：compose / healthcheck / migrations / 一键启动验证

## Day 2 · 缓存、限流与成本控制

**一句话**：缓存是降本利器，但一致性、租户隔离和过期策略必须一起设计。

**核心知识**

- 精确缓存 key：tenant + doc version + query hash + prompt version + model。
- 语义缓存按相似度命中，命中率高但有串答案风险；要设阈值、TTL、可关闭。
- 限流按用户/租户/模型维度；保护上游配额和成本。
- token 成本统计：输入/输出分开，检索/rerank 也算。
- 预算告警：日/月限额，异常流量自动降级。

**速查**

```text
cache_key = sha256(tenant | doc_version | prompt_version | model | query)
```

**常见坑**

- 缓存 key 不带版本，文档更新后仍返回旧答案。
- 语义缓存阈值太低，把不同意图的问题混在一起。

**面试口述**

> 语义缓存的风险是什么？怎么防止串答案？

**深入理解**
- **机制**：精确缓存按 key 命中，语义缓存按向量相似度命中；缓存降低延迟和成本。
- **边界**：语义缓存可能串答案；文档更新/权限变化会让缓存过期；缓存 key 必须带租户和版本。
**场景**：高频 FAQ 用精确缓存；语义缓存设高阈值、TTL、可关闭，并监控误命中。
**追问**：Q：缓存怎么失效？A：文档版本变化、权限变化、prompt/模型变化时失效；设 TTL 兜底。

**任务关联**：精确缓存 / 语义缓存开关 / 限流 / 成本对比

## Day 3 · 可观测性：trace、token、延迟、错误

**一句话**：没有 trace，线上问题只能靠猜。

**核心知识**

- 一次请求记录：request id、tenant、query、改写、召回 chunk/score、rerank、prompt 版本、模型、token、首 token/总延迟、引用、拒答原因。
- trace 要能回放：输入、输出、耗时、错误、成本。
- 指标：P50/P95、错误率、缓存命中率、token/请求、单次成本。
- 日志分级：INFO 业务事件、WARN 可恢复异常、ERROR 需处理。
- 告警：错误率、P95、成本、上游限流。

**速查**

```text
最小 dashboard：
请求量 / P95 首 token / 错误率 / 缓存命中 / 平均 token / 单次成本
```

**常见坑**

- 只记录最终答案，不记录检索和 prompt；无法定位是召回还是生成问题。
- 日志里打印完整用户隐私/文档内容，造成合规风险。

**面试口述**

> 一次 RAG 请求要记录哪些字段？为什么？

**深入理解**
- **机制**：trace 记录一次请求的完整调用链；指标聚合延迟、错误、token 和成本。
- **边界**：只记录最终答案无法定位问题；日志含隐私会合规风险；采样率太高成本高。
**场景**：记录 request id、召回 chunk/score、prompt 版本、模型、token、首 token/总延迟、引用/拒答。
**追问**：Q：线上问题怎么复现？A：用 trace 的输入、检索结果、prompt 和模型参数重放。

**任务关联**：Langfuse/OTel / trace 字段 / 指标表

## Day 4 · 评测回归与 CI

**一句话**：评测要像单测一样，每次改动都能跑、能比较、能阻止回归。

**核心知识**

- 固定评测集 + 版本；每次 PR 跑检索/生成指标。
- 设阈值和允许波动；LLM judge 成本高时抽样。
- 失败样本人工复核；结果存档，支持版本对比。
- 评测要覆盖：正常、边界、无答案、越权、注入。
- 报告要能回答：变好了吗？哪类问题变差？成本/延迟多少？

**速查**

```text
CI 门禁：Recall@5 >= 0.85 且 faithfulness >= 0.85 且 P95 < 2.5s
```

**常见坑**

- 评测集和训练/调参数据混在一起，分数虚高。
- 只看平均分，忽略某一类问题大幅退化。

**面试口述**

> 怎么把 RAG 评测接入 CI？阈值怎么定？

**深入理解**
- **机制**：评测 CI 在每次 PR 跑固定集，阈值阻止回归；结果存档支持版本对比。
- **边界**：judge 成本高要抽样；评测集太小波动大；阈值太严会阻塞正常迭代。
**场景**：PR 跑 50 条评测，Recall/faithfulness 不低于 baseline，P95 不超预算。
**追问**：Q：阈值怎么定？A：用历史波动和业务容忍度定，允许小波动，关键指标单独告警。

**任务关联**：50 条评测 / CI 脚本 / 阈值 / 报告 v2

## Day 5 · 压测与性能优化

**一句话**：先定位瓶颈，再优化；不要凭感觉换模型。

**核心知识**

- 分段计时：鉴权、检索、rerank、prompt、模型、DB、序列化。
- 压测阶梯增加并发，观察吞吐/延迟拐点。
- 常见瓶颈：上游配额、连接池、DB、rerank CPU、上下文过大。
- 优化手段：缓存、批处理、连接复用、并发限流、上下文裁剪。
- 报告写清环境、并发、数据量、P95、错误率和优化前后对比。

**速查**

```text
20 并发 → P95 2.8s；优化缓存后 1.9s；
瓶颈：rerank 占 45%，模型首 token 占 35%
```

**常见坑**

- 只压 healthcheck，不压真实链路。
- 压测环境和生产差距太大，数据不可参考。

**面试口述**

> P95 很高，你怎么定位是检索、rerank 还是模型慢？

**深入理解**
- **机制**：压测找容量边界和瓶颈；分段计时区分检索、rerank、模型、DB 和序列化。
- **边界**：只压 healthcheck 没意义；压测环境与生产差异大；长尾请求会拉高 P95。
**场景**：20/50 并发阶梯加压，记录吞吐、P95、错误率和资源使用。
**追问**：Q：P95 高先看什么？A：trace 长尾、连接池、上游限流、DB 慢查询和上下文大小。

**任务关联**：k6/locust / 分段计时 / 优化记录 / 压测报告

## Day 6 · 交付：README、架构图、视频、文章

**一句话**：面试官先看 README，再决定要不要看代码。

**核心知识**

- README：问题、架构、启动、指标、取舍、失败复盘、限制。
- 架构图：接入、ingestion、检索、生成、评测、观测。
- 3 分钟视频：问题 → 演示 → 指标 → 取舍。
- 技术文章：背景 → 方案 → 数据 → 失败 → 结论。
- 仓库清理：无密钥、无大文件、commit 清晰、tag v1.0。

**速查**

```text
README 结构：
1. 一句话价值
2. 架构图
3. Quick Start
4. 评测结果
5. 关键取舍
6. 已知限制
```

**常见坑**

- README 只有安装命令，没有指标和取舍；无法证明能力。
- 视频只是录屏不说话，观众不知道在解决什么。

**面试口述**

> 用 10 分钟讲项目一，你会怎么组织？

**深入理解**
- **机制**：README 是项目入口，架构图是认知地图，指标是可信度，失败复盘是深度。
- **边界**：只有安装命令无法证明能力；指标没有口径会被质疑；视频太长没人看。
**场景**：README 首屏给出问题、架构、Quick Start、指标和限制；3 分钟视频讲取舍。
**追问**：Q：面试官最想看什么？A：你解决了什么问题、怎么验证、失败过什么、如果重做怎么改。

**任务关联**：README / 架构图 / 视频 / 文章 / tag v1.0

## Day 7 · 周复盘 + 项目一模拟面试

**一句话**：讲不清的地方，就是还没真懂。

**核心知识**

- 模拟追问：为什么这样切分？为什么 hybrid？rerank 延迟？多租户？评测怎么建？
- 每个技术选择准备替代方案和代价。
- 记录被问住的 5 个点，补数据/补实验。
- 更新简历 bullet，确保每个数字有来源。

**速查**

```text
项目一 10 问：
切分 / embedding / hybrid / rerank / 引用 / 拒答 /
多租户 / 评测 / 成本 / 失败复盘
```

**常见坑**

- 只准备“成功故事”，被问失败就慌。
- 指标说不清口径，面试官会怀疑真实性。

**面试口述**

> 项目一最难的三个决策是什么？替代方案是什么？

**深入理解**
- **机制**：模拟面试检验结构、取舍和抗压；录音回听比自我感觉可靠。
- **边界**：只背答案会被追问击穿；只讲成功不讲失败显得不真实。
**场景**：20 分钟项目深挖，记录被问住的 5 个点，补数据/实验/故事卡。
**追问**：Q：被问住怎么办？A：承认边界，拆解问题，给假设和验证方式，不要编数据。

**任务关联**：W8 周测 / 模拟面试 / 复盘 / 简历 bullet
